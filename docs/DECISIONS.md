# Decisions and history

What was decided and why, grouped by area. Search this when you need the reason for something; you
don't need to read it before starting work. Open work is in [ROADMAP.md](./ROADMAP.md). How each
area works now is in its `CLAUDE.md` and in [ARCHITECTURE.md](./ARCHITECTURE.md).

Add one entry per decision, under its area, newest last: `- D Mon YYYY: what was decided, and why.`
Measurements and investigation notes belong here, not in code comments.

This file was started on 14 Oct 2026, from notes previously kept in `CLAUDE.md` and a `notes/` folder (since removed).
Earlier history is in git.

## Data pipeline

- 20 Mar 2026: the "all datasets" CSV, CSVW and XLSX files are generated by `data:spreadsheets` and
  served as static files from `/files/{file}`, rather than generated per request. The script uses
  the API's own `filterIndicators`/`filterDatasets`/`generateXLSX`/`generateCSV`, so the files match
  what the API would return.

## API and back end

### Correctness

- 9 Sep 2026: `filterIndicators.ts`'s fast path (a single named indicator looked up through
  `summaryStats.indicatorLookup`, with no scan) now covers every `hasGeo` value, by checking the one
  found dataset with `makeDatasetGeoFilter`. An early version compared area codes only, and silently
  gave wrong results for `hasGeo` values that are geography levels or types (`hasGeo=ltla`). So the
  fast path calls `makeDatasetGeoFilter` rather than reimplementing its three cases (area code,
  level, type).
- 11 Sep 2026: `hasGeo`'s "no filter" value is `any` on every endpoint. The metadata endpoints used
  to use `all`, which reads as "only datasets covering every geography". `all` is now an ordinary,
  invalid value everywhere.
- 11 Sep 2026: the same bug turned up three times. A function that can return `{ error, message }`
  instead of its normal result had a caller that used the result without checking. Hence
  `hasGeo=all` gave a 500 instead of a 400 in `getFilteredData.ts`, and twice in `getTaxonomy.ts`
  and its route. All three are fixed. Every caller of `filterIndicators`, `makeDatasetFilter` and
  similar must check `.error` straight away.
- 11 Sep 2026: a calendar-invalid but correctly shaped `time` (for example `2020-02-30`) gave a 500.
  `isValidDay`/`isValidMonth` (`validationHelpers.ts`) now check real dates with `Temporal`, not
  just the shape.
- 11 Sep 2026: the data endpoint's `geo`/`geoExtent` are case-insensitive. `makeGeoFilter.ts`
  (`src/lib/api/data/helpers/`, not the geo library's function of the same name) now upper-cases
  codes, as every `/geo/*` route already did. Before, a lowercase code silently matched nothing.
- 11 Sep 2026: `excludeMultivariate` no longer excludes an indicator named explicitly, on the
  metadata endpoints as on the data endpoint. It only applies to indicators pulled in broadly by
  `topic` or `all`. Before, `/metadata/indicators/population-by-age-and-sex?excludeMultivariate=true`
  gave a misleading 404.
- 11 Sep 2026: every route validates its query parameters. `/geo/lookup/{code}` and
  `/metadata/indicators/{indicator}/dimensions/{dimension}` were the last two that didn't. Both take
  no parameters, so any parameter is now a 400 instead of being ignored.
- 11 Sep 2026: the data endpoint was split into two routes by how many indicators they return,
  replacing one route whose response shape depended on how many indicators happened to match
  (`filterDatasets.ts`'s old `singleIndicator` guess: `topic === 'all'` and an `indicator` resolving
  to exactly one slug).
  - `/api/v1/data.{format}` is always grouped by indicator, even for zero or one match.
  - `/api/v1/data/{indicator}.{format}` is always one indicator, ungrouped. It rejects
    `topic`/`indicator`/`excludeMultivariate`, gives a 404 for an unknown slug (or one excluded by
    `hasGeo`, not distinguished, as on `/metadata/indicators/{indicator}`), and skips
    `isOversizedRequest`, which can never be true for one indicator (it needs all three of large
    time, large indicators and large geography).
  - Both route handlers set `params.singleIndicator` explicitly.
  - This was a breaking change, made deliberately while the API is not yet publicised. The front end
    moved at the same time: `makeDataUrl` sends a plain-string `indicator` to the single-indicator
    route and an array to the multi-indicator route.
  - The reasoning for consumers is in
    [docs/api/important-notes.md](./api/important-notes.md#the-two-data-endpoints-and-what-they-replaced).
- 11 Sep 2026: an empty result is a 200, not `400 No data available for the selected filters.`
  - The multi-indicator route returns an empty collection.
  - The single-indicator route returns the usual shape with empty values. The 400 remains only for a
    `measure` value matching nothing, where there is no value column to build an empty shape around.
  - `filterJSONStat`'s `length === 0 → null` guard (`filterDatasets.ts`) now fires only when the
    measure dimension (always last) is empty.
  - This exposed a bug in `toJSONStat`: its `dim.count !== 1` shortcut assumed a single-category
    dimension could never be filtered to zero. Checked against `employment-rate-ni`, a single-period
    indicator, with a non-matching `time`.
  - It also exposed a second bug in `generateCSVW.ts`, which chose its Dublin Core fields by
    `datasets.length === 1` rather than the `singleIndicator` flag used for its `indicator` column.
    Both now use the flag.
- 11 Sep 2026: `geoLevel` accepts different values on different routes, and response envelopes
  differ between routes. Both were kept and documented, not changed. The data routes and the
  navigation routes use different, legitimately different, geography hierarchies.

### Performance

The request path is `+server.ts` → `getFilteredData.ts` → `filterIndicators.ts` →
`filterDatasets.ts` (`filterJSONStat` per dataset) → `dataFormatters.ts`, or
`generateXLSX.ts`/`generateCSV.ts`. Measured with the benchmarks in `src/lib/api/data/`
(`npm run test:bench`).

- 9 Sep 2026: added Vitest benchmarks, with request shapes taken from real pages
  (`__fixtures__/queryShapes.ts`), and `src/test/mockAppServer.ts` so `$lib/data` can be imported
  under plain Vitest. `read()` from `$app/server` throws `__SVELTEKIT_TRACK__ is not defined`
  outside SvelteKit, so before this, nothing that imported `$lib/data` (most of `src/lib/api/`) could
  be tested or benchmarked.
- 9 Sep 2026: the data cube is held in memory, parsed once per process (top-level await in
  `getFilteredData.ts`, cached in `src/lib/data/index.ts`). Its size affects cold start and memory,
  not request time, so making the file read faster won't help requests.
- 9 Sep 2026: request cost grows with the number of combinations of the filtered dimensions, not
  with the size of the output. `dimsToCols` walks every combination and checks each for a value. A
  request with several loosely filtered dimensions can be slow even when few observations have
  data. Profile with real request shapes, not just large results.
- 9 Sep 2026: the `filterIndicators.ts` fast path is about 24–27× faster than a scan
  (multi-indicator or topic queries). With `hasGeo` set, it is only about 2× slower than the plain
  lookup.
- 9 Sep 2026: `toJSONStat` no longer `structuredClone`s every key of the shared cube per request. It
  copies only what it replaces: `size` (`.slice()`) and each dimension's `category` object, whose
  `index`/`label` are always replaced whole, never mutated. Everything else is shared by reference.
  The plain `json` format went from about 0.66 ms to 0.37 ms. Getting this wrong would corrupt the
  shared cube for later requests. It was checked by running several requests in a row (including the
  label-trimming and `includeNames` branches), then re-running an earlier broad request and comparing
  the output byte for byte. That check was not kept as a committed test.
- 9 Sep 2026: `cols.json`, the format every chart requests, had two optimisations:

  - `dimsToItems` and `itemsToCols` were merged into one walk (`dimsToCols`), so no intermediate
    array of `{ index, values }` objects is built.
  - `makeColFill` now resolves each output column to an array reference once, instead of looking up
    `data[dims[i].key]` per item.

  The fixture went from about 2.46 ms to 1.7–1.8 ms. `cols.json` is now about 4.7× slower than
  `json`, a wider gap than before, because `json` gained more from the clone fix above. It is still
  the format most worth optimising. The `makeColFill` style (build a specialised closure once, from
  the request's flags and resolved arrays, instead of branching per row) is the pattern to follow in
  similar loops.

- 9 Sep 2026: `generateCSV.ts` no longer uses d3-dsv's `csvFormat`, which was about 86% of its time.
  It ran a `Date` check, a string conversion and a regex test on every cell. Instead, a hand-written
  `formatValue`/`csvFormatRows` uses the same quoting rule (quote if the value contains `"`, the
  delimiter or a line break), with `indexOf` instead of a regex, and skips numbers, which never need
  quoting. `inferColumns` now looks only at each dataset's first row, since every row of a dataset
  has the same keys. The "download all" CSV went from about 14–15 ms to 10 ms. What remains is
  necessary work. d3-dsv is still used by the pipeline scripts.
- 9 Sep 2026: XLSX generation moved from exceljs to `documonster`, for accessibility rather than
  speed. The GOV.UK guidance
  ([Making spreadsheets accessible](https://analysisfunction.civilservice.gov.uk/policy-store/making-spreadsheets-accessible-a-brief-checklist-of-the-basics/))
  requires:
  - every data table to be a native Excel Table, with Excel's automatic filter buttons turned off
    (`filterButton: false` on every column of all three tables);
  - named heading styles (`Heading 1`/`Heading 2`, through `Workbook.defineCellStyle` and
    `Cell.applyCellStyle`);
  - a workbook-wide default font (`defaultFont` through `Workbook.getModel`/`setModel`).
- 10 Sep 2026: `documonster` upgraded from 0.13.1 to 0.14.0. That release fixed two problems found
  while profiling the migration and reported upstream: `TextEncoder.encode()` was called once per
  XML tag, and identical column/cell styles were not deduplicated. `generateXLSX.bench.ts` went from
  about 90–105 ms before the migration to about 12–13 ms, roughly 7–8× faster.

### Streaming

- 9 Sep 2026: XLSX output is a stream. `generateXLSX`/`dataToSpreadsheet` always return a `Readable`
  from `Workbook.toStream`, which serialises the same in-memory model as `toBuffer`, Tables
  included. `+server.ts` converts it with `Readable.toWeb()` and sends no `Content-Length`, since
  the compressed size isn't known until the end. `generate-spreadsheets.ts` pipes it to disk with
  `pipeline()`.
  - `Stream.WorkbookWriter`, the row-by-row writer, was not an option: it doesn't support Tables at
    all, and Tables are required (see above).
  - Writing the data with the streaming writer and then reopening the file to add Tables was
    rejected. Reopening rebuilds the whole in-memory model, so it is slower than building it once.
- 9 Sep 2026: how much the XLSX stream helps depends on the number of worksheets. `toStream` sends
  data between ZIP entries, and each worksheet is one entry. Checked by logging the time of each
  chunk:

  - A single-indicator download, with one large sheet, came out as 2 chunks, the first 99.7% of the
    file, about 20 ms before the end. Time to first byte and total time were the same as before.
  - `indicator=all`, with 104 sheets, came out as 46 chunks over about 6 s of an 11.5 s build. Time
    to first byte was about 27% faster (10.5 s → 7.7 s), at no cost to total time.

  For a new single-sheet case, log chunk times (`for await (const chunk of stream)` with
  `performance.now()`) before assuming streaming helps.

- 9 Sep 2026: a `Buffer` passed straight to `new Response(buffer)` is measurably slower to send than
  the same bytes as a one-chunk `ReadableStream`, and the gap grows with size. Below about 200 KB it
  doesn't matter. At 8 MB, in isolated tests, time to first byte was about 5× slower and total time
  about 30% slower. SvelteKit's Node adapter (`setResponse`) streams any `Response.body`, but not
  equally efficiently. This applies to any route that still returns a whole `Buffer`, such as CSV.
- 9 Sep 2026: JSON formats stay fully buffered; streaming them is closed.
  - Prototyped for `rows.json`. `JSON.stringify` is already one fast native call, and splitting it
    up is slower overall: about 6.5 ms buffered against 8.7–19 ms streamed, depending on batch size,
    for a time to first byte that drops from about 6.5 ms to 0.03 ms.
  - The common chart requests (`chartLatestBroadGeo`, `singleValueSingleArea`) already take under
    1 ms, and the heaviest common one (`chartTimeSeriesBroadGeo`) about 1.6 ms, far less than network
    latency.
  - `cols.json` has no natural row-by-row form, so it wasn't prototyped.
  - Worth reopening only if typical responses become much larger, or request volume much higher.

### Caching

- 9 Sep 2026: no `Cache-Control` headers are set on API routes. The production site is behind
  Cloudflare, which handles server and edge caching. `Cache-Control` would still let browsers and
  other API clients reuse responses; that is in [ROADMAP.md](./ROADMAP.md).

## Front end

- 11 Sep 2026: `makeDataUrl` (`src/lib/utils.ts`) is the only place that builds data URLs, apart
  from three download links on `indicators/[code]/+page.svelte`. It chooses the route by the type of
  `indicator`, not its length: a string goes to the single-indicator route, and any array (even with
  one item) to the multi-indicator route.

## Build and deploy

- 9 Mar 2026: static assets are served from the app container, not a CDN bucket
  (`ENABLE_S3_ASSETS=false`). Serving them from a bucket was set up in 2025, because the container
  serves data files as well as code, and those grow with every new indicator. The options
  considered were (from the former `notes/asset-hosting.md`):

  1. route asset paths to a bucket behind the same domain, as hosting platforms do (hard to set up
     here);
  2. serve all assets from a separate domain, the existing ONS `cdn.ons.gov.uk` pattern, which
     SvelteKit supports through `paths.assets` (the one implemented);
  3. serve only data files from a separate domain, which needs every path prefixed by hand, and the
     container still serves CSS and JS;
  4. do nothing, and rely on caching.

  It was turned off (in 2025, and finally in March 2026) because of glitches in the app, possibly
  caused by caching. We won't go back to serving assets separately: the app is already served from
  behind Cloudflare, so splitting out the assets added complexity for no real benefit. The
  `Makefile` and `Dockerfile` still contain the switch, to be removed (see ROADMAP.md).
