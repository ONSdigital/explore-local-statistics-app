# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"Explore Local Statistics" is an ONS (Office for National Statistics) SvelteKit app that lets users browse UK statistical indicators by area (region, local authority, etc.) via maps, charts and tables, and exposes the same data through a public JSON/CSV/XLSX API.

## Commands

- `npm run dev` — start the dev server
- `npm run build` / `npm run preview` — production build / preview it locally
- `npm run check` — svelte-kit sync + svelte-check (TypeScript/Svelte type checking)
- `npm run lint` — `prettier --check .` + `eslint .`; `npm run format` to auto-fix formatting
- `npm run test:unit` — Vitest, run once (`vitest --watch=false`); a single file: `npx vitest run src/path/to/file.test.ts`
- `npm run test:integration` — Playwright, builds and previews the app first (see `playwright.config.ts`); tests live in `tests/`
- `npm run audit` — `auditjs ossi` dependency vulnerability scan

Equivalent `make` targets (`lint`, `test`, `audit`, `build`, `build-local`, `run`) wrap these npm scripts for Concourse CI (`ci/*.yml`, `ci/scripts/*.sh`) and Docker builds; CI currently treats `make lint` as a no-op (see the `lint:` target in `Makefile`).

## Data pipeline (separate from the app's runtime)

The app does not fetch data live — all indicator/geo data is pre-processed into static files under `src/lib/data/` (JSON, gzipped CSV, XLSX) that get bundled at build time. These are regenerated via scripts in `scripts/`, run in this order:

1. `npm run data:download` — pulls raw CSVW datasets into `scripts/raw-data/` (a nested git checkout of the [explore-local-statistics-data](https://github.com/ONSdigital/explore-local-statistics-data) repo, whose branch is set in `scripts/config/data-repo-version.json`)
2. `npm run data:metadata` — generates CSVW metadata JSON per dataset
3. `npm run data:checks` — pre-flight consistency checks, writes `scripts/data-update-changelog.txt`
   (1–3 combined: `npm run data:ingest`)
4. `npm run data:generate` — builds the combined JSON-stat data cube (`src/lib/data/json-stat*.json`) from `scripts/config/manifest_metadata.csv`, which drives the indicator taxonomy
5. `npm run data:spreadsheets` — generates the downloadable XLSX files
6. `npm run meta:sitemap` — generates the sitemap
   (4–6 combined: `npm run data:build`)

Geo boundary/area data has its own pipeline: `npm run geo:generate` (`scripts/make-geo-data.ts`) and `npm run geo:clusters` (`scripts/make-clusters.ts`), combined as `npm run geo:all`.

The full data-update workflow (branching, editing the manifest, QA, going live) is documented in `scripts/managing-updates.md` — read it before touching anything under `scripts/` or `scripts/config/`.

## Architecture

**Routing** (`src/routes/`) is split into two route groups:

- `(app)/` — the user-facing SvelteKit pages (home, `/areas/[code]`, `/indicators/[code]`, area/indicator search, embeds).
- `(api)/api/` — a versioned public HTTP API (`/api/v1/...`) for data, geo lookups and metadata, plus health/alive checks. Route handlers are thin: they validate query params (`src/lib/api/utils.ts`, `src/lib/api/data/helpers/requestValidators.ts`) and delegate to functions in `src/lib/api/`.

**`src/lib/api/`** holds all data-access/query logic, independent of routing, organized by domain:

- `data/` — filtering the indicator data cube and generating output formats (CSV/CSVW/XLSX) — entry point `getFilteredData.ts`
- `geo/` — area lookups by code/name/postcode/lng-lat, parent/child/sibling/similar-area relationships
- `metadata/` — indicator/dimension/taxonomy metadata

Each domain's `getX.ts` files are the public entry points; `helpers/` subfolders hold internal filtering/formatting utilities. Route handlers under `(api)/api/` and page `load` functions under `(app)/` both call into this layer rather than duplicating logic.

**`src/lib/data/`** contains the pre-generated static data files (see Data pipeline above) plus `index.ts`, a small dual-mode JSON reader: in Vite/dev it uses `import.meta.glob` + SvelteKit's `$app/server` `read`; in the built Node server it reads from disk directly. Data is read once and cached in memory — treat these files as an immutable data layer, not something to mutate at runtime. `json-stat.json`/`json-stat-summary.json` are the core data cube consumed by `getFilteredData.ts`.

**Config** is split between `src/lib/config.ts` (colours/palettes and misc app constants) and `src/lib/config/` (geo levels, geo lookups, measures, nav map sources, topics) — check both before adding new constants.

**Components** (`src/lib/components/`): `charts/` (Bar, Line, Map, Table, Beeswarm, Pyramid, Sparkline, wrapped by `IndicatorChart.svelte`/`ChartDataLoader.svelte`), `modals/`, `nav/` (area/indicator search, pagination), `visuals/` (map primitives). This project uses the Svelte port of the ONS Design System, `@onsvisual/svelte-components` (see README for `npm link` workflow when developing against a local copy of that library).

**Logging**: `src/lib/logger.ts` (pino) is wired into `console.*` globally in `src/hooks.server.ts` for non-dev environments — don't reintroduce raw `console.log` calls expecting dev-only behaviour.

## Build/deploy notes

- The SvelteKit adapter is chosen at config time in `svelte.config.js`: Vercel adapter if `VERCEL` env var is set, otherwise the Node adapter — relevant if changing build/runtime behaviour.
- `SVELTEKIT_BASE_PATH`, `SVELTEKIT_ASSETS_PATH` and `SVELTEKIT_APP_VERSION` env vars configure the base path, CDN asset path and app version for production builds (see `Makefile` and `svelte.config.js`).
- Production static assets can be served from a CDN bucket instead of the app container (`ENABLE_S3_ASSETS` in `Makefile`); currently disabled.

## Performance notes for the data API

Request path for `/api/v1/data.[format]` (the main data endpoint) and its helpers:

`+server.ts` → `getFilteredData.ts` → `filterIndicators.ts` (dataset-level filter) → `filterDatasets.ts` → `filterJSONStat` per dataset (dimension-level filter) → `dataFormatters.ts` (`dimsToCols`/`colsToRows`/`toJSONStat`) → response, or `generateXLSX.ts`/`generateCSV.ts` for those formats.

- **The data cube is in-memory, not re-read per request.** `getFilteredData.ts` does `const cube = await readData('json-stat')` as a top-level await, and `src/lib/data/index.ts` caches by key after first read — so `json-stat.json` (~11MB) is parsed once per server process, not per request. Cold-start/memory footprint scales with this file, not request latency; don't chase "read the file faster" here.
- **No `Cache-Control` headers are set anywhere in `src/routes/(api)/`** (checked, none exist) — **still true, not addressed.** The deployed app sits behind Cloudflare, which already covers server/edge-side caching, so that's not a gap to fix here. `Cache-Control` also governs the _client's own_ cache, though (browser, or any API consumer) — without it, repeat requests for the same URL always go back out over the network instead of being served locally. That's the remaining opportunity, and it's independent of Cloudflare.
- **Cost scales with the cartesian product of filtered dimensions, not the output size.** `dimsToCols` (`dataFormatters.ts` — the fused replacement for the old separate `dimsToItems`/`itemsToCols` pair, see below) walks every combination of the filtered dims and checks each one's sparsity as it goes; a request with several loosely-filtered dimensions can be expensive even if few observations actually have data. Profile with real query shapes, not just "large result" requests.
- **`filterIndicators.ts`'s fast path now covers every `hasGeo` value, not just `'any'`.** It still looks up a precomputed `summaryStats.indicatorLookup` index instead of scanning the full dataset array for `topic === 'all'` + a single indicator string, and now checks any `hasGeo` constraint against just that one already-found dataset (`makeDatasetGeoFilter`) instead of falling back to a full scan — measured ~24-27x faster than the genuine scan path (multi-indicator/topic-filtered queries; see `filterIndicators.bench.ts`), with the `hasGeo`-set case only ~2x slower than the plain lookup (one extra per-dataset check, not a scan). Watch for this if touched again: an early version of this fix used an area-code-only equality check and silently returned wrong results for `hasGeo` values that are geo _levels_ or _types_ (e.g. `hasGeo=ltla`) rather than a specific area code — caught by testing against `makeDatasetGeoFilter`'s three-way (area code / level / type) behaviour, which is why the fast path delegates to that function rather than reimplementing the check.
- **`isOversizedRequest` (`requestValidators.ts`) only rejects requests where time, indicator _and_ geo are all simultaneously "large"** (`&&`, not `||`) — e.g. `time=all` across every indicator for a single small area is allowed, as is one broad geo group for a single time period. **Still not addressed.** The real "download data" links on indicator pages (`/api/v1/data.xlsx?indicator=<slug>&time=all`) hit exactly this gap: single indicator + `time=all` + default `geo=all` is a genuinely broad request that isn't rejected — and it's now measurably the most expensive shape by far (~113ms for `xlsx`, ~10ms for `csv`, vs ~1.6ms for the equivalent `cols.json`/chart request — see benchmark numbers below). Worth revisiting this heuristic with those numbers in mind.
- **`toJSONStat` (`dataFormatters.ts`) no longer `structuredClone`s every cube key.** It used to deep-clone every top-level key of the shared in-memory cube per request to avoid mutating it; now it only copies what it actually writes to — a `.slice()` of `size`, and a shallow per-dimension clone of just the `category` object each dim's `index`/`label` get replaced on (both are always replaced wholesale, never mutated in place, so no deeper copy is needed) — everything else is reference-copied. Cut the plain `json` format's time roughly in half (~0.66ms → ~0.37ms on the same fixture). Verified with a dedicated mutation-safety test (several requests in a row, including ones that exercise the label-trimming/`includeNames` branches, then re-checking an earlier broad request comes back byte-identical) since getting this wrong would corrupt the shared cube across requests.
- **`cols.json` — the format every chart in the app actually requests (see `IndicatorChart.svelte`/`ChartDataLoader.svelte`)** — went through two rounds of optimization this session: fusing `dimsToItems`+`itemsToCols` into one `dimsToCols` walk (no more materializing an intermediate array of `{ index, values }` objects — one full object plus one copied array per combination — before filling columns), then having `makeColFill` resolve each output column to a direct array reference once (via the now-already-built `data` object) instead of doing a `data[dims[i].key]`-style property lookup per item. Net effect on the `cols.json` fixture itself: ~2.46ms → ~1.7-1.8ms (~30% faster). The gap to plain `json` actually _widened_ to ~4.7-4.8x though, because `json`'s own `structuredClone` fix (above) was a much bigger relative win — `cols.json` is still the highest-traffic format by far and the right target for further formatting-hot-loop work, but don't be surprised the ratio moved in the "wrong" direction; it reflects `json` getting faster, not `cols.json` getting slower.
- **XLSX generation (`generateXLSX.ts`) now uses `documonster`, not `@protobi/exceljs`.** This was a deliberate, accessibility-driven migration, not a performance one: GOV.UK accessibility guidance ([Making spreadsheets accessible: a brief checklist of the basics](https://analysisfunction.civilservice.gov.uk/policy-store/making-spreadsheets-accessible-a-brief-checklist-of-the-basics/)) requires every data table to be marked up as a native Excel Table (essential/"E"), with the filter buttons Excel adds to a Table automatically turned off — done here via `filterButton: false` on every column across all three tables (`table_of_contents`, `notes`, and the per-indicator data tables). `documonster` also sets the workbook-wide default font properly now (`Workbook.getModel`/`setModel`'s `defaultFont` field), replacing the old `StylesXform` monkey-patch. Net perf: **~110-115ms, roughly 10-25% slower than the original exceljs baseline (~90-105ms)** — an accepted trade-off, not a regression to chase. Two real, profiled, library-internal inefficiencies account for most of the remaining gap and were filed upstream against `documonster` (not fixable from this app's call site — worth re-benchmarking `generateXLSX.bench.ts` if a future `documonster` release addresses either): its XML stream writer calls `TextEncoder.encode()` once per XML tag rather than batching writes (~13-16% of total time in profiling); and column/cell styles can't be deduplicated across columns with identical content because `columnSetNumFmt`/`columnSetStyle` mutate each column's own persistent style object in place rather than accepting a shared reference (~13% of total time) — confirmed the _output_ is still correctly deduplicated (few distinct `<xf>` entries), so it's wasted computation on the way to a correct result, not a correctness or file-size bug.
- **`generateCSV.ts` no longer uses d3-dsv's `csvFormat`.** Profiling showed `csvFormat` was ~86% of `generateCSV`'s total time — for every cell it did a `value instanceof Date` check (always false; JSON-Stat values are only ever strings/numbers/null), an unconditional string coercion, and a **regex `.test()`** call to decide whether CSV-quoting was needed. Replaced with a hand-rolled `formatValue`/`csvFormatRows` matching the exact same quoting rule (quote iff the value contains a `"`, the delimiter, or a line break) but using `indexOf` checks instead of regex and skipping the check entirely for numbers (a JS number's string form can never need quoting). Also fixed `inferColumns` to sample just the first row of each dataset instead of scanning every row — every row within one dataset is guaranteed to share the same key set (see `colsToRows`, which always writes the same fixed columns onto every row). Combined: ~14-15ms → ~10ms on the "download all data" CSV fixture (~30% faster). d3-dsv itself is still a dependency (used throughout `scripts/` for the data pipeline) — only `generateCSV.ts` stopped using it. The remaining cost here is genuinely necessary CSV-formatting work, not more low-hanging fruit.
- `dataFormatters.ts`'s `makeColFill` remains the reference example of the codebase's preferred optimization style: build a specialized closure once outside the loop (based on the boolean flags _and_ the already-resolved output-array references for a given request) instead of branching or doing property lookups per row — match this pattern rather than introducing per-item conditionals if optimizing similar hot loops.

### Benchmarks

A Vitest benchmark suite exists under `src/lib/api/data/` — run it with `npm run test:bench` (or `npx vitest bench <path>` for one file). It measures the pipeline above against representative request shapes rather than synthetic worst cases:

- `__fixtures__/queryShapes.ts` — the shared request-param fixtures, each commented with which real UI call site it represents (chart line/table, chart map/bar, single-value, full download). Keep these in sync if those call sites' param-building logic changes.
- `getFilteredData.bench.ts` — end-to-end pipeline timing across the fixtures above, plus a same-query format comparison (`cols.json`/`rows.json`/`json`).
- `filterIndicators.bench.ts` — isolates the dataset-level filter's fast path vs. scan path. All four cases currently in it take the fast path except the two that filter by topic or request every indicator — if adding a case meant to represent the _scan_ path, make sure it actually falls through (check against `filterIndicators.ts`'s current fast-path condition first).
- `helpers/generateXLSX.bench.ts` — isolates spreadsheet generation from filtering, using the full-download fixture. This is what was used to compare `@protobi/exceljs` against `documonster` like-for-like during the migration (now complete) — keep using it the same way for any future XLSX-generation change, including if either of the upstream `documonster` issues noted above gets fixed.

**`src/test/mockAppServer.ts`** (wired in via `test.setupFiles` in `vite.config.ts`) mocks `$app/server`'s `read()`, which `src/lib/data/index.ts` depends on. That function needs SvelteKit's dev/build runtime and throws (`__SVELTEKIT_TRACK__ is not defined`) under plain Vitest — so before this, nothing importing `$lib/data` (i.e. most of `src/lib/api/`) could be unit-tested or benchmarked at all. The mock reads the same files straight off disk instead; it's only valid pre-build (a built app's asset URLs are content-hashed, which the mock doesn't attempt to resolve), so it's for `test:unit`/`test:bench`, not for exercising the real production asset path.

### Streaming (investigated for both XLSX and JSON; not pursued)

Neither part of the pipeline streams — `+server.ts` always returns a fully-built `Response`, and `dataFormatters.ts`/`generateXLSX.ts` build their entire result in memory before anything is returned. Both were prototyped and benchmarked (real total-time _and_ time-to-first-byte measurements, not just reasoned about) before concluding against implementing either:

- **XLSX — genuinely faster on both axes, but blocked by a hard requirement, not a performance judgement call.** A `Stream.WorkbookWriter`-based prototype measured ~3x faster _total_ time (not just TTFB — `documonster`'s buffered `Workbook`/`Table` API does real second-pass work the streaming writer skips) and ~18x faster time-to-first-byte (e.g. ~6.3s → ~0.35s TTFB on a large multivariate download). This contradicts the "streaming trades total time for TTFB" assumption below for JSON — it does not hold for documonster's two XLSX writers, because the buffered one does avoidable extra work, not because streaming is free. It was still **not implemented**: `documonster`'s streaming `WorksheetWriter` has no native Excel Table support at all ("a streaming worksheet has no ... tables ... those need a second pass over cells this writer has already discarded, which is the whole point of it" — its own source comment) — and native Table markup is the same hard GOV.UK accessibility requirement noted above, not optional. A two-pass approach (stream the bulk write, then reopen buffered just to layer `Table.add` on top) was considered and rejected: reopening needs `Workbook.readFile` to fully rebuild the same in-memory model the direct buffered path already builds, so it's strictly slower than just using the buffered writer once, not a real middle ground. Revisit only if `documonster` adds Table support to its streaming writer upstream.
- **JSON formats (`cols.json`/`rows.json`/`json`) — the opposite result; not worth it.** Prototyped by streaming the serialization step for `rows.json` (the most naturally streamable of the three — a flat array of row objects; `cols.json`'s column-oriented shape, `{ areacd: [...], value: [...] }`, doesn't have a natural row-by-row streaming form the way `rows.json`'s does, so it wasn't prototyped separately once the underlying question was settled). Unlike XLSX, there's no redundant "second pass" to skip — `JSON.stringify` is already one highly-optimized native call, and splitting it into many smaller calls is strictly slower in aggregate (confirmed even at the best batch size tested: total time went from ~6.5ms buffered to ~8.7-19ms streamed depending on batch size, for a TTFB drop from ~6.5ms to ~0.03ms). And the real-traffic baseline is already too fast for TTFB to matter: the two most common real chart shapes in `queryShapes.ts` (`chartLatestBroadGeo`, `singleValueSingleArea`) complete in well under 1ms already; even the heaviest common one (`chartTimeSeriesBroadGeo`, ~1.6ms per `getFilteredData.bench.ts`) is dwarfed by ordinary network RTT in real usage. Concluded closed, not just deferred — re-litigating this would need a fundamentally different baseline (much larger typical payloads, or much higher request volume where the per-request CPU cost compounds) to be worth revisiting.
